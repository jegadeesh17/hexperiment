# Implementation Plan: hexperiment-benchmark

## How to use this plan

- Work the tasks in order. Each task ends with the whole suite green and `ruff` clean, so a later task never has to repair an earlier one. The one exception is the results tests (task 18): they need the committed `results.json` and are written after it exists, so no earlier task is left with a failing or skipped test.
- Run all commands from the repository root. Every task ends with the same two full commands, `.venv/Scripts/python -m pytest hexperiment/tests -q` and `.venv/Scripts/python -m ruff check hexperiment`; the "Verify" line of a task names the focused test files to run first.
- Tests live next to the module they cover (`tests/test_benchmark_<module>.py`) and are written in the same task as the module. Where `design.md` lists a Hypothesis property for a module, the task adds it.
- Signatures, algorithms, the text of every mechanism (data, leaky lines, clean lines, prediction) and the test lists are in `design.md`. This plan names what to build and where, not how.
- The order follows "Build order and the first run" in `design.md`:
  - Code and tests first: tasks 1 to 10 (spec, mechanisms, cases, data, execution, summary and report, runner and entry points, README skeleton).
  - Smoke runs, one task per group of mechanisms, run by the builder with `run_benchmark.py --only <key>`: tasks 11 to 15, then the report in task 16.
  - The complete run and the two README texts are the owner's: task 17.
  - The results tests that need the committed `results.json`: task 18. Final check: task 19.
- **No task runs a benchmark case inside the test suite.** The suite never starts `hexperiment run` and never starts a training script. The tests reach the edges through the injected `launcher`, `find` and clock arguments of `runner.main` and `execution.run_app`, with fakes that write `verdict.json` files. The smoke runs of tasks 11 to 15 are commands the builder types in a terminal, not tests.
- The core rules still hold: pure modules stay pure, `tests/test_architecture.py` stays green, no module-level mutable state, `hexperiment/__init__.py` exports the same seven names, the runtime dependencies stay `pandas`, `numpy` and `scikit-learn`, and nothing under `hexperiment/src/hexperiment/` or `apps/` is changed. The only file outside `hexperiment/benchmark/` and `hexperiment/tests/` that the builder changes is `hexperiment/pyproject.toml` (task 1); the owner also edits `.github/workflows/pages.yml` in task 17.
- Do not edit `requirements.md`, the steering files or `design.md`. If the design is ambiguous or contradicts itself, record the question in the report at the end of the task instead of guessing.
- **Owner's answers** (start of "Open questions" in `design.md`) apply everywhere: every recommendation is accepted; the eight leakage-type names are the ones checked on PMC10499856 and are used word for word; the tests find `hexbench` through `pythonpath = ["benchmark"]` in `[tool.pytest.ini_options]` of `hexperiment/pyproject.toml`, **not** through a line in `conftest.py` (so the "Layout" text of `design.md` that mentions `conftest.py` does not apply); the complete run is done by the owner; the smoke runs are done by the builder.
- **No tuning toward a check.** Nothing in any task may be changed because a ghost fired or did not fire. The predictions in `design.md` are not targets.
- **Test time.** The benchmark adds about 83 test functions (about 330 collected items with parametrisation), all in process except one test that starts a Python process (task 9). Data is generated once per test module. There is no suite time limit (`hexperiment-kiro`, Requirement 7.4): report the suite time and the ten slowest tests (`--durations=10`) at the end of every task, and never lower Hypothesis settings to save time.
- Generated scripts are strings and are not linted, but `ruff check hexperiment` covers `hexperiment/benchmark/` and the new tests. Write the benchmark code with type hints on public functions, small functions, frozen dataclasses and no `print` (use `emit`, see task 9).
- **Owner tasks** (17) are done by the project owner after the builder has finished tasks 1 to 16: the complete run must happen in everyday use so that the recorded environment and run time are real. The builder skips it and lists it in its report. Task 18 is the builder's again, after the owner has committed `results.json` and the README text.
