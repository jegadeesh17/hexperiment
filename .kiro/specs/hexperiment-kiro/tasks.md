# Implementation Plan: hexperiment-kiro

## How to use this plan

- Work the tasks in order. Each task ends with the whole suite green, so a later task never has to repair an earlier one.
- Run all commands from the repository root: `.venv/Scripts/python -m pytest hexperiment/tests -q` and `.venv/Scripts/python -m ruff check hexperiment`. Both must pass at the end of every task.
- Tests live next to the module they cover (`tests/test_<module>.py`) and are written in the same task as the module. Each new module has example-based tests and at least one `hypothesis` test where `design.md` lists a property.
- Signatures, algorithms, the contents of the Kiro files and the test lists are in `design.md`. This plan names what to build and where, not how.
- The core rules still hold: pure modules stay pure, `tests/test_architecture.py` stays green, no module-level mutable state, only `canary.py` imports `subprocess`, and `hexperiment/__init__.py` exports the same seven names.
- The core's runtime dependencies stay `pandas`, `numpy` and `scikit-learn`. The MCP SDK is an optional extra (task 7).
- **Human steps.** The `builder` agent may write `.kiro/hooks/**`, `.kiro/workflows/**` and `.kiro/agents/ghost-hunter.json`, but not `docs/` or other `.kiro/` files, and cannot run `kiro-cli`. A step marked **Owner** is done by the project owner after the builder finishes; the builder skips it and lists it in its report.
- Every real training run in a new test goes through `FakeRunner` or a stub `RunApp`. Only two new tests start Python (task 5 and task 7). If task 9 finds the suite above 85 seconds, report which tests are slowest instead of lowering Hypothesis settings.
